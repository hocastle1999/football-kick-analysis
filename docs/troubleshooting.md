# 문제 해결 기록

졸업 프로젝트 코드를 다시 정리하면서 찾은 문제와 해결 과정을 적는다.

## 1. 관절 좌표와 공 좌표가 서로 다른 프레임을 가리킴

### 문제
키포인트 파일(`.npy`)의 행 수가 원본 영상의 프레임 수보다 적었다.
논문에 쓴 113개 파일을 원본 영상과 비교한 결과는 다음과 같다.

| 데이터 | 파일 수 | 행이 모자란 파일 | 가장 많이 빠진 경우 |
|---|---|---|---|
| 무게중심 (`keypoints_csv_with_ball`) | 63 | 54 | 25프레임 (영상 104프레임, 파일 79행) |
| 디딤발 (`keypoints_foot_with_ball`) | 50 | 48 | 1프레임 |

### 원인
두 스크립트가 "i번째 행"을 서로 다르게 이해하고 있었다.

1. `openpose.py`는 관절을 찾은 프레임만 저장했다. 사람이 아직 화면에 없거나 검출에 실패한 프레임은 건너뛰었다.
   그래서 파일의 i번째 행은 "영상의 i번째 프레임"이 아니라 "관절을 찾은 i번째 프레임"이었다.
2. `add_ball.py`는 영상을 처음부터 읽으며 i번째 프레임의 공 위치를 파일의 i번째 행에 붙였다.

앞쪽에서 k프레임이 빠지면 그 뒤로는 모든 행에서 관절은 (i+k)번째 프레임, 공은 i번째 프레임의 값이 된다.

### 영향
- 임팩트 추정은 크게 틀어지지 않았을 가능성이 높다. 공은 차기 전까지 멈춰 있으므로,
  공 위치가 몇 프레임 앞의 값이어도 "발이 공에 가장 가까운 순간"은 비슷하게 잡힌다.
- 임팩트 이후는 영향을 받는다. 관절은 이미 공을 찬 뒤인데 공은 아직 제자리에 있는 것으로 기록된다.
  임팩트 뒤 5프레임의 공 위치를 입력으로 쓰는 디딤발 모델이 여기에 해당한다.
- 얼마나 정확도에 영향을 줬는지는 아직 측정하지 않았다(다시 평가할 때 확인한다).

### 해결
`kick_analysis/extraction.py`에서 관절과 공을 같은 반복문 안에서 프레임마다 함께 뽑고,
못 찾은 프레임은 지우지 않고 NaN으로 남긴다. 결과의 i번째 행은 항상 영상의 i번째 프레임이다.
`tests/test_extraction.py`가 일부 프레임에서 검출이 실패해도 행과 프레임이 맞는지 검사한다.

### 배운 점
- 여러 단계가 같은 배열을 이어서 다룰 때는 "한 행이 무엇을 뜻하는지"를 한 곳에서 정해야 한다.
- 데이터를 지우면 뒤 단계가 알 수 없다. 빈 값은 지우지 말고 빈 값이라고 표시한다.
- 중간 결과물의 크기를 원본과 비교하는 간단한 검사만 있었어도 바로 드러났을 문제다.

## 2. 학습할 때와 분석할 때의 전처리가 달랐음

### 문제
같은 영상이라도 학습용 스크립트와 GUI가 모델에 넣는 값이 달랐다.

| 항목 | 학습 (`openpose.py`, `add_ball.py`, `train_*.py`) | 분석 (`test.py`) |
|---|---|---|
| 포즈 추정 모드 | `static_image_mode=False` (앞 프레임을 이어받아 추적) | `True` (프레임마다 새로 검출) |
| 관절을 못 찾은 프레임 | 지움 | 0으로 채움 |
| 임팩트를 찾는 거리 | 3D (공의 z는 임팩트 때 발의 z로 고정) | 사실상 2D (프레임마다 공의 z = 발의 z) |
| 라벨 순서 | 폴더 이름을 정렬해 그때그때 결정 | 코드에 직접 적음 |

### 원인
전처리 코드가 학습 스크립트와 GUI에 각각 따로 들어 있었고, 한쪽을 고칠 때 다른 쪽을 맞추지 않았다.

### 해결
전처리를 `kick_analysis` 패키지 한 곳으로 모았다. 학습 스크립트와 GUI는 같은 함수를 부른다.

- 좌표 추출: `extraction.KeypointExtractor` (추적 모드 사용)
- 임팩트 추정: `impact.find_impact_frame` (화면 좌표 x, y만 사용. 공에는 실제 깊이 값이 없다)
- 모델 입력 생성: `features.build_impact_sequence`, `features.build_foot_sequence`
- 숫자와 라벨 순서: `config.py`. 라벨 순서는 모델 파일에도 함께 저장한다.

### 배운 점
학습과 추론의 입력이 조금이라도 다르면 테스트 정확도가 실제 사용 성능을 보장하지 못한다.
전처리는 복사하지 말고 한 함수를 양쪽에서 불러 쓴다.

## 3. 모델을 통째로 저장해 다른 환경에서 불러오기 어려움

### 문제
`torch.save(model)`로 양자화한 모델 객체 전체를 저장했다. 이 방식은 파이썬 pickle이라
모델 클래스가 정의된 위치(학습 스크립트의 `__main__`)와 PyTorch 버전에 묶인다.
또 PyTorch 2.6부터 `torch.load`의 기본값이 `weights_only=True`로 바뀌어 이런 파일은 기본 설정으로 열리지 않는다.

### 해결
가중치(`state_dict`)와 입력 크기, 라벨 순서만 저장한다(`models.save_checkpoint`).
양자화는 저장할 때가 아니라 불러올 때 적용한다(`models.load_checkpoint(quantized=True)`).
동적 양자화는 학습 데이터가 필요 없어서 불러온 뒤 바로 적용할 수 있다.

### 배운 점
저장 파일에는 데이터(가중치와 설정)만 넣는다. 코드까지 함께 직렬화하면 코드 구조를 바꿀 때마다 파일이 깨진다.

## 4. 임팩트 프레임이 영상마다 접촉 직전이기도 하고 직후이기도 함

### 문제
영상별 임팩트 프레임을 한 장에 모아 보니, 발이 공에 닿기 직전인 영상과 공이 이미 떠난 영상이 섞여 있었다.
모델은 "임팩트 앞 2프레임부터 6프레임"을 입력으로 받는데, 그 기준점이 영상마다 한두 프레임씩 달랐던 것이다.

### 원인
- 24fps에서 차는 발은 한 프레임에 화면 폭의 15% 안팎을 움직인다. 접촉은 두 프레임 사이에서 일어나고,
  "발과 공이 가장 가까운 프레임"은 그 앞뒤 중 우연히 더 가까운 쪽이 된다.
- 공이 검출된 프레임만 후보였다. 임팩트 근처에서 공을 놓치면 후보에서 빠진다.

### 해결
공은 차기 전까지 멈춰 있다는 점을 이용했다. 검출이 가장 많이 모인 곳을 공의 자리로 정하고,
차는 발끝이 공의 가장자리를 지나는 시점을 앞뒤 프레임 사이에서 보간해 구한다(`impact.find_impact`).
공 검출이 일부 빠져도 공의 자리는 알 수 있고, 기준점이 항상 "접촉 시점"으로 같다.

### 배운 점
- 숫자(정확도)만 보지 말고 중간 결과를 눈으로 확인해야 한다. 임팩트 프레임을 한 장에 모아 본 것이 계기였다.
- 측정 간격(프레임)보다 빠른 사건은 가장 가까운 측정값을 고르는 대신 사이를 보간하는 편이 일관된다.

## 5. 한 클래스만 다른 날 찍혀 있어 정확도가 부풀려짐

### 문제
디딤발 모델이 aligned 클래스를 늘 100% 맞혔다.

### 원인
aligned 영상 10개만 다른 날, 다른 장소, 다른 사람이 찍은 것이었다(해상도도 720p와 1080p로 다르다).
화면 좌표를 그대로 입력으로 쓰면 사람이 서 있는 위치와 크기만으로 "그날 찍은 영상"을 구분할 수 있다.
촬영 조건의 영향을 없앤 정규화 좌표로 바꾸고, 사람을 통째로 빼고 시험하니 aligned를 하나도 맞히지 못했다.

### 해결
- 평가에 사람 단위 분할을 넣었다(`scripts/evaluate.py`). 같은 사람이 학습과 시험에 함께 들어가지 않는다.
- 좌표를 공 기준으로 정규화해 촬영 위치와 거리의 영향을 줄였다(`features.build_normalized_pose`).
- 디딤발 결과는 화면에 참고용이라고 표시한다. 근본 해결은 aligned를 같은 조건으로 다시 찍는 것이다.

### 배운 점
- 클래스와 함께 바뀌는 다른 조건(날짜, 장소, 사람, 해상도)이 있으면 모델은 더 쉬운 쪽을 배운다.
- 무작위 분할의 높은 점수는 "새 사람, 새 촬영에서도 맞는다"를 뜻하지 않는다. 무엇을 빼고 시험할지 정하는 것이 평가 설계다.
